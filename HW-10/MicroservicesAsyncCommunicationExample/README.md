# Задачи через RabbitMQ

Два сервиса не вызывают друг друга. Сервис A принимает HTTP-запрос и кладёт задачу в очередь. Сервис B забирает её из брокера и возвращает факт выполнения тоже через брокер.

| Контейнер | Роль |
| --- | --- |
| `job-api` | Сервис A. `POST /jobs` и `GET /jobs/{id}`. Статус хранится в памяти процесса. |
| `booking-worker` | Сервис B. Читает очередь `tasks`, около 3 секунд «обрабатывает», публикует `JobCompleted` в очередь `results`. |
| `rabbitmq` | Брокер и management UI на порту 15672. |

Тема задачи — бронирование переговорки. Контракт между сервисами — сообщения в очередях, а не HTTP. Стек: ASP.NET Core и MassTransit 8.3.6 (9-я версия без лицензии не стартует).

```
POST /jobs
  -> job-api пишет статус ACCEPTED и отправляет сообщение в очередь tasks
  -> сразу 202
booking-worker читает tasks, ждёт ~3 с, отправляет JobCompleted(id, result, completedAt) в results
job-api читает results и ставит статус DONE
GET /jobs/{id} -> DONE и результат
```

## Запуск

Нужны Docker Desktop и свободные порты 8080, 5672, 15672.

Из этой папки (где лежит `docker-compose.yml`):

```powershell
docker compose up --build
```

Подождите, пока в логе `job-api` и `booking-worker` появится `Bus started`. После этого API отвечает на порту 8080. Swagger UI: http://localhost:8080/swagger

Остановка: `Ctrl+C`, затем при необходимости `docker compose down`.

## Сценарий

PowerShell, из любой папки, когда контейнеры уже запущены:

```powershell
$body = '{"roomId":"11111111-1111-1111-1111-111111111111","startTime":"2026-11-10T10:00:00Z","endTime":"2026-11-10T11:00:00Z"}'
$tmp = New-TemporaryFile
curl.exe -s -D - -o $tmp -X POST http://localhost:8080/jobs -H "Content-Type: application/json" --data-raw $body
Get-Content $tmp -Raw
$id = (Get-Content $tmp -Raw | ConvertFrom-Json).id
Start-Sleep -Seconds 4
curl.exe -s http://localhost:8080/jobs/$id
```

`POST` возвращается сразу, не через 3 секунды:

```http
HTTP/1.1 202 Accepted
Content-Type: application/json; charset=utf-8

{"id":"8f0c2e3a-1b4d-4e5f-9a6b-7c8d9e0f1a2b","status":"ACCEPTED"}
```

`id` каждый раз новый. Сразу после `POST` тот же `GET` ещё показывает `"status":"ACCEPTED"` без результата. Примерно через 3 секунды:

```json
{"id":"8f0c2e3a-1b4d-4e5f-9a6b-7c8d9e0f1a2b","status":"DONE","result":"Комната 11111111-1111-1111-1111-111111111111 забронирована с 2026-11-10T10:00:00.0000000Z по 2026-11-10T11:00:00.0000000Z","completedAt":"2026-11-08T14:31:05.1234567Z"}
```

Неизвестный id — `404`.

Лог обработчика:

```powershell
docker compose logs booking-worker
```

Там есть строки `Начата обработка задачи ...` и через ~3 секунды `Задача ... выполнена`.

## Очереди в management UI

Откройте http://localhost:15672 и войдите как `guest` / `guest`.

Вкладка **Queues and Streams**:

| Очередь | Кто пишет | Кто читает |
| --- | --- | --- |
| `tasks` | `job-api` при `POST /jobs` | `booking-worker` |
| `results` | `booking-worker` после обработки | `job-api` |

Пока воркер обрабатывает задачу, у `tasks` сообщение в колонке **Unacked**. После подтверждения оно исчезает, а в `results` на короткое время появляется `JobCompleted`, пока его не заберёт `job-api`.

Рядом MassTransit создаёт свои exchange. Для сценария нужны именно очереди `tasks` и `results`.

## Почему POST отвечает 202

`202 Accepted` значит: запрос принят, но работа ещё не сделана. `job-api` только сохраняет статус `ACCEPTED` и кладёт сообщение в `tasks`. Бронь делает другой процесс, и это занимает около 3 секунд. Клиент не ждёт окончания — он получает `id` и потом спрашивает `GET /jobs/{id}`.

`200 OK` здесь был бы неверным: к моменту ответа результата ещё нет.

## Если сервис B упал посередине обработки

Подтверждение брокеру (ack) уходит только после того, как метод обработки нормально завершился. Все ~3 секунды сообщение висит неподтверждённым.

Если в этот момент процесс B убить, соединение с RabbitMQ обрывается, ack не отправлен. Брокер возвращает сообщение в очередь `tasks`. Когда обработчик снова поднимется, он получит ту же задачу ещё раз.

Это гарантия **at-least-once**: сообщение не теряется, но может быть доставлено повторно. Это не exactly-once и не at-most-once (при at-most-once брокер снял бы сообщение с очереди сразу при выдаче, и падение B его бы потеряло).

Исключение внутри обработчика — другой случай. MassTransit тогда уносит сообщение в очередь ошибок `tasks_error`, а не молча возвращает его в `tasks`. Падение процесса до ack как раз возвращает исходное сообщение.

### Защита от дублей

Повторная доставка — нормальный исход at-least-once, поэтому обработчик помнит id уже выполненных задач в памяти процесса. Если тот же id приходит ещё раз в живой процесс, он пишет в лог `Повторная доставка задачи ..., пропускаю`, подтверждает сообщение и не публикует второй `JobCompleted`.

Память умирает вместе с процессом. После `docker kill` новый процесс этого списка уже не видит и выполняет задачу ещё раз. На стороне A повторный `JobCompleted` с тем же id не затирает уже записанный результат: статус остаётся `DONE`.

Отдельной базы нет — так и задумано в задании. Список обработанных id живёт только в процессе B, статусы задач — только в процессе A. Перезапуск контейнера обнуляет его память.

## Бонус: сообщение возвращается, если убить B до ack

Удобнее удлинить паузу, чтобы успеть убить контейнер. В `docker-compose.yml` у сервиса `booking-worker` добавьте переменную и пересоздайте его:

```yaml
environment:
  RabbitMQ__Host: rabbitmq
  RabbitMQ__Username: guest
  RabbitMQ__Password: guest
  Processing__DelaySeconds: "20"
```

```powershell
docker compose up -d --build booking-worker
```

Дальше, сразу после `POST`:

```powershell
docker kill hw10-worker
```

В UI у очереди `tasks` сообщение переходит из **Unacked** обратно в **Ready** — брокер его вернул. Затем:

```powershell
docker start hw10-worker
docker compose logs --tail 30 booking-worker
```

В логе та же задача начинается снова. `GET /jobs/{id}` по-прежнему один: `DONE` и один результат.

Для обычной проверки эту переменную ставить не нужно: по умолчанию пауза 3 секунды.
